# 路线图

> 本路线图覆盖两条路线的近期修补、中期能力对齐与中长期能力扩展。
> 状态说明：🔲 未开始 · 🔨 进行中 · ✅ 已完成
>
> 注意：下面按**能力层级**排列，用于说明「还缺什么」，**不代表数据流上的先后关系**。
> 两条路线是并列探索的，见 [architecture.md](architecture.md)。

## 能力分层

```
L4  决策层    机组组合 / 储能调度 / 风险成本          🔲
L3  场景层    概率预测 · 时空相关场景生成              🔲   ← 中长期重点
L2  治理层    Active/Candidate · 门禁 · 审计          ✅  仅路线 A（energy-tsf）
L1  模型层    谱系 · 滚动评测 · 集成                  ✅  两条路线均有（B 更宽）
L0  数据层    y/H/F 协议 · 时序切分 · 时点对齐         ✅  两条路线均有
```

两条路线合计覆盖 L0–L2，但**没有任何一条路线单独覆盖全部三层**：
路线 A 缺宽模型谱系，路线 B 缺治理与长期运行。往上（L3 场景层、L4 决策层）是下一阶段的主要增量。

## 中期（两条路线的能力对齐与移植）

我们不做二选一，而是把每条路线上验证有效的能力移植给另一条。

| 项 | 方向 | 状态 | 说明 |
|---|---|---|---|
| 滚动评测内核移植进路线 A | B → A | 🔲 | 把 `train_validation_test()`（训练内调参 + 多窗口滚动 + 三种集成）作为路线 A modeling/update 轨道的执行引擎 |
| 发布治理能力补进路线 B | A → B | 🔲 | 让路线 B 的评测结果也能走 Candidate → 门禁 → Active |
| 统一模型能力契约 | 双向 | 🔲 | `model_catalog()` 能力声明 ↔ `ProviderCapabilities`，避免给不支持的模型喂未来协变量 |
| 两条路线的对照评测 | 双向 | 🔲 | 同一数据集、同一指标下对照两条路线的效果与成本，形成选型指引 |
| 训练经验跨场站复用 | B | 🔲 | 从《训练经验报告》提取可复用经验，辅助新场站冷启动选型，最终仍由滚动验证检验 |
| NWP 发布时间 / 版本自动核验 | B | 🔲 | 当前路线 B 不核验预报发布时间，存在信息泄漏风险 |
| 基础模型可用性 | 双向 | 🔲 | 路线 B 仅 zero-shot；路线 A 要求本地权重与钉死版本，需提供权重准备脚本 |
| 多场站规模化 | B | 🔲 | 路线 B 已有 Ray/Dask/Spark 后端，可与路线 A 的场站资产库对接 |

## 中长期（场景层与决策层）

| 项 | 状态 | 说明 |
|---|---|---|
| 概率 / 分位数预测 | 🔲 | 两条路线目前都只做点预测。电网调度需要 P10/P50/P90，改造越晚成本越高 |

## 明确的非目标

以下内容**不在**本项目范围内，避免范围蔓延：

- 不做通用 AutoML 框架（不追求在任意表格 / 视觉任务上通用）。
- 不做气象预报本身（NWP 作为外部输入）。
- 不做 SCADA / 数据采集与硬件接入。
- 不复制基础模型权重到资产库，不在运行时下载权重。

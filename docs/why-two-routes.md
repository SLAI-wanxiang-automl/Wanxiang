# 为什么是两条路线

这是本项目被问得最多的问题，所以直接把答案写在前面。

## 简短版

因为「Agent 怎么做新能源预测」本身还没有定论，而两种主流范式各有明显短板：

- **Harness 路线**（`energy-tsf`）把 Agent 放在仓库外，用契约约束它，换来确定性与可追责，
  代价是灵活度受限、依赖宿主 Agent。
- **Agentic Workflow 路线**（`energy-expert`）把 Agent 放在仓库内，让它编排工具与流水线，
  换来自主度与可解释性，代价是不可复现、且没有发布治理。

这是个还**没有被验证出胜负**的架构选择。我们不做二选一，而是两条都跑，用真实场景对照。

## 详细版

### 1. 两条路线的根本分歧

| | 路线 A · Harness | 路线 B · Agentic Workflow |
|---|---|---|
| Agent 在哪 | 仓库**外**（Codex / Claude Code / Pi / DeepSeek） | 仓库**内**（`agent.py`） |
| 谁编排流程 | SKILL 契约 + 确定性 CLI | LLM 工具调用 |
| 数值计算 | 全部确定性代码 | 确定性流水线（LLM 只解释） |
| 模型谱系 | 8 个 Provider，聚焦 | 宽：统计/ML/深度/Prophet/sktime/基础模型 + 分布式 |
| 长期运行 | ✅ 预测 / 回测 / 受约束更新 | ❌ 评测完即止 |
| 发布治理 | ✅ 门禁 / 分轨权限 / 审计日志 | ❌ |
| 可复现性 | 强（config_hash + 输入指纹） | 中（依赖锁定，LLM 环节有随机性） |
| 依赖重量 | 轻（pandas/sklearn/lgbm/xgb） | 重（torch/ray/prophet/…） |
| Python | 3.12+ | 3.10–3.13 |

注意：**两条路线的能力覆盖并不对称**。路线 A 独有发布治理与长期运行，
路线 B 独有宽模型谱系与滚动评测。这也是保留两条路线的实际价值——它们互补，而非二选一。

### 2. 为什么不合并成一条

合并会同时牺牲两边的优势：

- 若统一到 Harness：要砍掉路线 B 的模型谱系与分布式评测能力，或给场站侧塞进 torch + ray。
- 若统一到 Agentic Workflow：要放弃路线 A 的门禁、权限与审计，这在需要追责的交付场景里不可接受。
- 依赖重量本身就是硬约束：路线 A 要上场站，路线 B 要横向对比几十个模型，两者的最优依赖集不同。

所以是**两个独立包**：各自有自己的 `pyproject.toml`、测试和 Python 版本要求，
可以单独安装、单独引用、单独演进。

### 3. 为什么放进同一个仓库

既然是两条路线，为什么不干脆开两个仓库？

- **对外只有一个入口**：一个链接、一份 README、一张对照表，而不是让人自己猜两个项目什么关系。
- **社交证明集中**：star / fork / issue 不分散在两个 0 起步的仓库里。
- **对照与移植有地方放**：路线间的能力对齐、选型指引、统一 CI 和路线图，放在任何一个子包里都不合适。
- **历史完整保留**：用 `git subtree` 导入，两个项目的 commit 历史都还在，没有重写。

### 4. 常见误解

**问：两个包都在做「新能源出力预测的 Agentic AutoML」，是不是重复造轮子？**
不是同一件事的两种实现，而是**同一个命题的两种架构解法**。
路线 A 问的是「怎么让 Agent 的每一步都可审计」，路线 B 问的是「怎么让 Agent 自主完成评测并讲清楚理由」。
两者的成功标准不同，不能直接用一个替换另一个。

**问：应该先用哪个？**
看场景：

| 你的场景 | 走哪条 |
|---|---|
| 要长期在真实场站跑，出事要能追责 | 路线 A · Harness |
| 要横向对比模型、出实验结论 | 路线 B · Agentic Workflow |
| 要发论文 / 做基线对比 | 路线 B |
| 要交付给电网或业主并过验收 | 路线 A |
| 不确定 | 两条都装，先用 B 选模型，再用 A 上线 |

**问：LLM 到底参不参与决策？**
都不参与**数值**决策。路线 B 的排行榜由验证集指标决定，LLM 只负责读 `experiment_log.json`
写解释性报告；路线 A 的全部数值计算由确定性代码完成，宿主 Agent 只把自然语言转成结构化请求。
区别在于：路线 B 的 LLM 参与**流程编排**（调用哪些工具），路线 A 的 LLM 只做**意图理解**。

**问：以后会合并成一条吗？**
短期不会。目标是**能力互相移植**，而不是合并：
把路线 B 的滚动评测内核与模型谱系移植进路线 A 的执行引擎，
把路线 A 的发布治理与长期运行能力补进路线 B。见 [路线图](roadmap.md)。

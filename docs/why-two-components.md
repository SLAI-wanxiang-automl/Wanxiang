# 为什么是两个组件

这是本项目被问得最多的问题，所以直接把答案写在前面。

## 简短版

因为它们解决的是**两个不同阶段**的问题，强行合成一个会两头都不做好：

- 建模引擎要的是**宽**：尽可能多的模型、尽可能灵活的搜索、越快出对比结论越好。
- 运行系统要的是**稳**：尽可能少的变动面、可追责的发布、可预测的线上行为。

把「宽」和「稳」塞进同一个包，结果通常是：为了稳而砍掉模型谱系，或者为了宽而牺牲发布治理。

## 详细版

### 1. 关注点不同

| | 建模引擎 | 运行系统 |
|---|---|---|
| 提问 | 这个场站该用哪个模型？ | 模型上线之后怎么一直跑？ |
| 时间尺度 | 一次实验（分钟~小时） | 长期运行（月~年） |
| 核心资产 | leaderboard、超参、集成权重 | Active 方案、审计日志、门禁记录 |
| 失败代价 | 重跑一次 | 线上预测错误、无法归因 |
| 变更频率 | 高（不断加模型） | 低（变更必须过门禁） |
| 依赖 | 重（torch / neuralforecast / ray / prophet） | 轻（pandas / sklearn / lightgbm / xgboost） |

依赖重量这一条尤其关键。运行系统要部署到场站侧，装一套 torch + ray + pyspark 是不现实的；
而建模引擎要在离线环境里横向对比几十个模型，轻量依赖又做不成事。
**分成两个包，运行系统就能只装自己那一半。**

### 2. 为什么不是「一个仓库两个目录」的代码合并

代码合并是可能的，但我们选择不合并，理由：

- 两个包的抽象层级不同（建模引擎是库，运行系统是 harness + CLI），合并后包结构会变得难以理解。
- 两者的发布节奏、测试策略、Python 版本要求都不同（引擎 3.10–3.13，运行时 3.12+）。
- 保持独立包，意味着可以单独引用、单独发版，也能被第三方单独使用。

所以本仓库用 **monorepo 承载、包保持独立** 的方式：`packages/` 下两个包各自有自己的
`pyproject.toml`、测试和 LICENSE，只是放在同一个仓库里共用一份品牌、文档、CI 与路线图。

### 3. 那为什么要放进同一个仓库

既然代码不合并，为什么不干脆开两个仓库？

- **对外只有一个入口**：一个链接、一份 README、一张架构图，而不是让人自己去拼两个项目。
- **社交证明集中**：star / fork / issue 不分散在两个 0 起步的仓库里。
- **跨组件的东西有地方放**：端到端示例、统一 CI、术语映射、路线图，放在任何一个子包里都不合适。
- **历史完整保留**：用 `git subtree` 导入，两个项目的 commit 历史都还在，没有重写。

### 4. 常见误解

**问：两个组件都在做「新能源出力预测的 Agentic AutoML」，是不是重复造轮子？**
不是。建模引擎做的是「**选**模型」，运行系统做的是「**用**模型并维护它」。
一个类比：建模引擎是实验室，运行系统是生产线。实验室负责找到配方，生产线负责每天按配方生产、
并在原料变化时调整。两者都需要，且接口清晰。

**问：能不能只用其中一个？**
可以，这也是分成两个包的原因：

- 只想横向对比模型、出实验结论 → 只用 `packages/energy-expert`。
- 已有确定的模型方案，需要长期运行与审计 → 只用 `packages/energy-tsf`。

**问：LLM 到底参不参与决策？**
不参与数值决策。建模引擎的排行榜由验证集指标决定，LLM 只负责读取 `experiment_log.json`
生成解释性报告；运行系统的数值计算全部由确定性代码完成，宿主 Agent 只负责把自然语言转成
结构化请求。这条边界是为了可复现与可审计。

**问：什么时候会合并成一个组件？**
不会。目标是让两层之间的**契约**更顺畅（建模结果自动成为运行系统的 Candidate），
而不是把两个包合成一个。见 [路线图](roadmap.md)。
